# M1 tcgen05 probe design and execution package (throwaway)

- **Date**: 2026-09-19
- **Purpose**: answer the full-scope fork decision question — **can sm120 reuse FlashMLA's existing tcgen05 (TMEM+UMMA) kernels**; the verdict decides whether M3/M4 take "full reuse" or the "PR#189-style SM80-MMA fallback".
- **Nature**: the probe artifact = the verdict; all probe changes are **throwaway** and never merge into mainline.
> Path migration (after the 2026-10-26 rebase): every `csrc/kernels/...` in this document should be read as `csrc/cuda_kernels/...` (directory renamed by the upstream 2026.09.30 refactor).

- **Target variant**: `csrc/kernels/sm100/decode/sparse/head64/instantiations/v32_h64.cu` (head64 sparse decode, V32, d_qk=576).
- **Probe verdict (measured on IOTA, 2026-09-19)**: ❌ **fallback B** — ptxas (CUDA 12.9) for the sm_120a target **does not support the tcgen05/Tensor Memory instruction family** (see §6.1).

## 1. Rationale (why a shim is needed)

Mechanisms verified (CUTLASS main, via online sources):

- `cutlass/arch/config.h`: the SM100 family is enabled by **exact match** --
  ```cpp
  #if (!defined(CUTLASS_ARCH_MMA_SM100A_ENABLED) && defined(__CUDA_ARCH__) && __CUDA_ARCH__ == 1000)
    ... #define CUTLASS_ARCH_MMA_SM100A_ENABLED  // the inner layer also requires __CUDA_ARCH_FEAT_SM100_ALL (i.e. -arch=sm_100a)
  #endif
  ```
  When compiling for sm120 (`__CUDA_ARCH__ == 1200`), all SM100 family macros are undefined.
- `cute/arch/config.hpp`: `CUTE_ARCH_TCGEN05_TMEM_ENABLED` and friends are enabled by one of `CUTLASS_ARCH_MMA_SM100A/SM100F/...` → they stay disabled under sm120 as well.
- CUTLASS has a separate family for sm120 (a dedicated `Sm120` tag, `mma_sm120.hpp`), but FlashMLA does not consume it → the cute tcgen05 UMMA atoms referenced by FlashMLA kernels do not take effect when compiling for sm120.

**Shim technique (finalized)**: predefine the SM100 family macros for sm120 **before** any cutlass/cute header is included. The cleanest implementation with zero source intrusion = **nvcc command-line `-D`**, because command-line macro definitions take effect **before** any header include, which is exactly "before the cutlass headers":

```
-DCUTLASS_ARCH_MMA_SM100_ENABLED
-DCUTLASS_ARCH_MMA_SM100A_ENABLED
-DCUTLASS_ARCH_MMA_SM100F_ENABLED
```

Dependency surface this relies on (verified locally):
- The main loop of head64 decode `kernel.cuh` uses `UMMA::make_umma_desc` (K-major K descriptor) + `UMMA::SmemDescriptor` + `cute/arch/tmem_allocator_sm100.hpp` (TMEM allocator) + the kerutils-local `SM100_MMA_F16BF16_WS_TS_NOELECT` atom.
- cute/arch/config.hpp mapping: `CUTE_ARCH_TCGEN05_TMEM_ENABLED`, `CUTE_ARCH_TMA_SM100_ENABLED`, `CUTE_ARCH_LDSM/STSM_SM100A_ENABLED` are driven by `CUTLASS_ARCH_MMA_SM100{,A,F}*` → predefining these three covers TMA + tcgen05 tmem.
- The `cutlass/arch/config.h` guard `#if (!defined(X) && __CUDA_ARCH__==1000 ...)` is skipped because the macros are already defined; the values come from the command line and the semantics are preserved.

**Safety**: `-D` affects every arch target of that .cu, so the probe performs an **SM120-only build** (`FLASH_MLA_DISABLE_SM100=1 FLASH_MLA_DISABLE_SM90=1`, leaving only compute_120a); there is no risk of accidentally enabling sm100 code on 90a/100a.

**Note**: if ptxas rejects the tcgen05 instructions at `compute_120a` → hard compile failure, which is the probe's failure signal (see §4). If individual macros are missing (extra gates in the tcgen05 atom bodies), add `-DCUTLASS_ARCH_MMA_SM101A/F`, `SM103A/F` alongside and retry.

## 2. FlashMLA gates that need adjustment (kerutils)

`csrc/kerutils/include/kerutils/device/common.h`:

```cpp
L60: KERUTILS_ENABLE_SM100A := __CUDA_ARCH__ >= 1000 && < 1200
L64: KERUTILS_ENABLE_SM103A := __CUDA_ARCH__ >= 1030 && < 1200
```

First probe experiment: let SM100A cover sm120 (`>= 1000 && < 1300`) while SM103A stays `< 1200` (the sm103-only tmem_ld reduction stays disabled for now and takes the fallback). This way every kernel body gated by `KERUTILS_ENABLE_SM100A` (head64 decode etc.) is entered when compiling for sm120.

```cpp
#if (defined(__CUDA_ARCH__) && (__CUDA_ARCH__ >= 1000 && __CUDA_ARCH__ < 1300))
#define KERUTILS_ENABLE_SM100A
#endif
```

Expected effect: at `compute_120a`, the head64 decode kernel body is no longer empty; whether it **compiles** and whether it is **numerically correct** are the two questions the probe must answer.

**Pass criteria**:
1. **Compilation**: `compute_120a` blows up (e.g. ptxas rejects tcgen05.mma on sm120 / missing macros / empty kernel) → the probe fails outright; record the offending primitive and take fallback B.
2. **Numerics**: once compilation passes, the V32 d_qk=576 case matches the reference (no NaN, max-abs/cosine within threshold) → the probe passes.
3. **Rough performance**: a crude timing of a simple kernel; a theoretical-bandwidth efficiency (measured bandwidth / 1.8TB/s or the measured peak) > ~50% is a viable signal (fine tuning happens in M5).

## 5. Local verification and residual unknowns (what the probe itself must answer)

**Local verification is complete** (2026-09-19, read-only audit against a copy of CUTLASS main shallow-cloned from a gh-proxy mirror; the exact re-check of FlashMLA pin `147f5673` is left to the IOTA build, which fetches it automatically through setup.py):

- `cutlass/arch/config.h`: the SM100A/F guards are `#if (!defined(...) && __CUDA_ARCH__==1000 ...)` → **command-line `-D` predefinition does bypass them** ✓.
- `cute/arch/tmem_allocator_sm100.hpp`: the TMEM allocation gate = `CUTE_ARCH_TCGEN05_TMEM_ENABLED` → covered by the three defines ✓.
- `cute/arch/mma_sm100_umma.hpp`: the UMMA instruction-body gate = `CUTE_ARCH_TCGEN05_F16F32_MMA_ENABLED` (the FF-BF16 variant, exactly what FlashMLA head64 uses) → covered by the three defines ✓.
- `cute/arch/copy_sm100_tma.hpp`: the TMA atom gate = `CUTE_ARCH_TMA_SM100_ENABLED` → covered by the three defines ✓.
- Observation: CUTLASS main has already added differentiated gates such as `TCGEN05_TMEM_EXCLUSIVE` / `UTFMMA_SCALED` for SM107 etc. → architectures genuinely differ at the tcgen05 instruction level; whether FlashMLA's BF16 UMMA can run directly on sm120 is still for the probe to answer.

**Genuinely unknown (answerable only by the probe's compile + real hardware)**: ① whether ptxas under `nvcc -arch=compute_120a` accepts tcgen05.mma / tmem-related PTX hits; ② whether the TMEM allocator is usable on sm120; ③ whether the numerical semantics match sm100. These are the entire reason the M1 probe exists.

## 8. Measured verdict record (2026-09-19, IOTA)

**Verdict: ❌ fallback B — sm120 cannot reuse FlashMLA SM100 tcgen05 kernels.**

### 8.1 Executive summary (the actual IOTA chain)
- **Environment calibration**: 2× IOTA (RTX PRO 6000 Blackwell Server, CC 12.0) in place; CUDA 12.9.86 + offline install of torch 2.14.0+cu130 (pypi wheels, get-pip `--no-index`, PEP 668 `--break-system-packages` user-install) + python3.12 headers.rsync (`~/py312-dev` + `CPATH` bridging a multi-arch pyconfig). See the addendum in `docs/sm120-m1-probe-patch/README.md`.
- **Compilation chain**: the SM120-only build (`FLASH_MLA_DISABLE_SM100=1 FLASH_MLA_DISABLE_SM90=1`, `compute_120a` only) was fully set up; the host pass (api.cpp) + the CUDA front end already pass (showing that the C++ layer/cutlass templates are fine on sm120).

### 8.2 Evidence chain for the probe verdict
1. **The first shim (command-line `-D` of the three SM100 macros) was abandoned**: `-D` **also takes effect in the nvcc host pass** → `CUTE_ARCH_TMA_SM90_ENABLED` is switched on in the host pass → `CUTE_HOST_DEVICE copy()` in `copy_sm90_tma.hpp` calls the `__device__` `synclog_emit_tma_*` → compile error. **Lesson**: a bare `-D` is unusable; the defines must go through the `config.h` guard (with its `__CUDA_ARCH__` check) so they stay off in the host pass.
2. **config.h range shim (the finalized probe method)**: the `CUTLASS_ARCH_MMA_SM100_ENABLED` guard `== 1000` → `1000..1300`; the `SM100A`'s `__CUDA_ARCH_FEAT_SM100_ALL` → merged into `__CUDA_ARCH_FEAT_SM120_ALL`. The host pass stays off (no `__CUDA_ARCH__`). **This shim gets the entire CUDA front end through** (tcgen05/UMMA/TMEM/TMA templates + compilation OK).
3. **Decisive ptxas rejection (1st)**: `Feature '.cta_group::1' not supported on .target 'sm_120a'`. The TMA load (cta mode) passes, but the cluster-semantics token is rejected by sm_120a.
4. **Decisive ptxas rejection (2nd, re-verified with the token stripped)**: after deleting every `.cta_group::1` token, `tcgen05.alloc / relinquish_alloc_permit / fence / wait / ld(.32x32b) / mma / commit` **all** report `Instruction ... not supported on .target 'sm_120a'`. **This disproves "it is only a token syntax problem"** — the instruction set of ptxas for the sm_120a target (CUDA 12.9) **lacks the Tensor Memory/tcgen05 system as a whole**.
5. **Corroborating evidence (architecture level)**: the CUTLASS pin of this brief puts the orthodox MMA implementation for SM120 in `mma_sm120.hpp`, using **`mma.sync` (register file, SM90 syntax style)**, `kind::f8f6f4`/f16 etc. — **the entire pin has no SM120 tcgen05 token at all**. The CUTLASS community's routing choice for SM120 (consumer Blackwell) = register-file MMA, consistent with the probe's measurements.

### 8.3 Impact on the plan
- **The M2§7 wiring checklist (8 rows based on "reuse") is void**, replaced by the dispatch changes for the register-file MMA route (see the plan §6 update).
- **M3/M4 baseline change**: no longer "translate all SM100 kernels"; instead **SM90/register-file MMA kernel family → sm120**. Key prerequisites (next pre-check): ① SM90 `mma.sync m16n8k16` and its variants are accepted by ptxas on sm_120a (highly likely, since CUTLASS sm120 is exactly mma.sync); ② availability on sm120a of the TMA/mbarrier usage in FlashMLA SM90 kernels (partly with cluster semantics); ③ the arch gates of the kerutils/cute SM90 atoms need to be widened from `==900` (same shim technique, device pass only).
- **Toolchain**: if tcgen05 is ever needed on consumer Blackwell, the tcgen05 support of CUDA 13.x ptxas/driver for sm_120a must be verified separately (not done this time; IOTA has CUDA 12.9 only). The current decision does not depend on it.

### 8.4 Leftovers
- IOTA `~/flashmla-sm120/` keeps the throwaway probe changes (config.h range shim, token stripping, torch mismatch patch, py312-dev, wheels cache) as a reuse baseline for the later M3R; they do not enter mainline. The local fork worktree is unpolluted (apart from the new docs).
